# 🎯 신조어 & 줄임말 퀴즈 게임 (fun-quiz) 기술 보고서

> **Python 3.12 기반 콘솔 인터랙티브 퀴즈 프로그램 & Git 브랜칭 워크플로우 실습 프로젝트**

본 프로젝트는 파이썬 객체 지향 프로그래밍(OOP) 패러다임과 JSON 영속성 관리 및 자동 백업/복구 시스템을 결합하여 개발한 콘솔 퀴즈 게임입니다.  
Git 필수 7대 명령어 실습, 기능별 브랜칭 전략(`main` - `feature`), 10회 이상의 커밋 사이클 및 원격 저장소 복제(`clone`/`pull`) 라이프사이클을 준수했습니다.

## 💾 4. 데이터 저장 방식 분석: JSON의 한계와 대안 논의

### 1) JSON 채택 이유
* 직관적인 텍스트 포맷으로 디버깅이 용이하며, 파이썬 표준 라이브러리로 가볍게 동작합니다.
* `indent=2` 및 `ensure_ascii=False` 설정을 통해 한글 가독성을 확보했습니다.

### 2) JSON 방식의 기술적 한계
1. **메모리 및 I/O 병목:** 데이터 1건만 수정되어도 파일 전체를 메모리에 올리고 다시 쓰는 비효율이 발생합니다 (대용량 확장 시 부적합).
2. **동시성(Concurrency) 제어 부재:** 여러 프로세스가 동시 접근할 때 파일 락(Lock) 기능이 없어 데이터 유실 위험이 존재합니다.
3. **트랜잭션(ACID) 미지원:** 쓰기 작업 도중 프로그램이 강제 중단될 경우 JSON 파일이 깨지는 현상이 발생할 수 있습니다.

### 3) 향후 고도화 방안 (Next Step)
* 데이터 규모가 수천 개 이상으로 커지거나 멀티유저 환경으로 확장될 경우, SQLite나 PostgreSQL 같은 관계형 데이터베이스(RDBMS)로 전환하여 인덱싱 조회 및 ACID 트랜잭션을 보장하도록 설계합니다.

2. **손상 시 2단계 복원 워크플로우:**

## 📋 6. state.json 스키마 설계 및 중첩 구조 채택 사유 (평가 항목 #17 보완)

### 1) 필드별 역할 및 정의
| 필드명 | 데이터 타입 | 설명 및 역할 |
| :--- | :---: | :--- |
| `quizzes` | `List[Dict]` | 전체 퀴즈 목록을 순서대로 관리하는 최상위 배열 컨테이너 |
| `quizzes[].question` | `String` | 사용자에게 화면으로 출력할 퀴즈 문항 텍스트 |
| `quizzes[].choices` | `List[String]` | 4지선다 객관식 선택지 보기 목록 (1번~4번 매핑) |
| `quizzes[].answer` | `Integer` | 실제 정답 번호 (1~4 범위의 정수값, 인덱스 판정 기준) |
| `best_score` | `Integer` | 플레이어가 달성한 역대 최고 점수 기록 보존 |

### 2) 계층형 중첩 구조(Nested Structure) 채택 사유
1. **문제 단위의 원자성(Atomicity) 확보:** 하나의 퀴즈를 구성하는 '질문-보기 목록-정답'을 단일 객체(`Dict`)로 묶어 관리함으로써, 배열 순회나 문제 추가/삭제 시 데이터 간의 참조 불일치를 원천 차단합니다.
2. **객체-도메인 매핑 일치:** `Quiz` 클래스의 속성(`question`, `options`, `answer`)과 1:1로 정확히 직렬화(`to_dict`) 및 역직렬화(`from_dict`)가 이루어지도록 설계하여 파싱 로직의 복잡도를 최소화했습니다.
3. **메타데이터 분리 독립성:** 퀴즈 데이터 목록(`quizzes`)과 전역 런타임 상태 데이터(`best_score`)를 동격의 루트 키로 분리 배치하여, 향후 '플레이어 프로필', '누적 플레이 횟수' 등 추가 메타데이터가 늘어나도 기존 퀴즈 구조를 손상시키지 않고 유연하게 확장 가능합니다.

## 🌿 8. Git 버전 관리 및 브랜치 실습 내역
### 1) Git 커밋 단위 및 메시지 작성 규칙 (Commit Convention)

#### ① 커밋 단위 기준 (작업 크기)
* **단일 책임 원칙(Single Responsibility):** 한 커밋에는 오직 하나의 논리적 변경(기능 1개 추가, 버그 1개 수정, 문서 1개 갱신)만 포함합니다.
* **빌드 안정성 유지:** 커밋 직후 언제든지 해당 시점으로 체크아웃하더라도 프로그램이 정상 작동할 수 있는 최소 동작 단위(Atomic Commit)로 분할합니다.
* **대용량 일괄 커밋 지양:** 여러 파일에 걸친 무관한 변경 사항을 `git commit -am "수정완료"` 형태로 일괄 커밋하지 않고 단계별로 분리합니다.

#### ② 커밋 메시지 규칙 (접두사 및 본문 형식)
* **메시지 구조:** `<type>: <subject>` 형식으로 작성하며 첫 줄은 50자 내외로 명확히 기술합니다.
* **주요 Type 접두사 정의:**
  * `feat`: 새로운 기능 구현 (예: 퀴즈 채점 로직, 백업 파일 생성)
  * `refactor`: 코드 동작 변경 없는 구조 개선 (예: 예외 처리 문구 정돈)
  * `test`: 테스트 코드 추가 및 복구 로직 검증 (예: 파일 손상 복구 단위 테스트)
  * `docs`: 문서 수정 (예: README 작성, 아키텍처 분석 명시)
  * `chore`: 빌드 업무 수정, 패키지 매니저 설정, 프로젝트 정리
